# MiniLcm ↔ LibLCM terminology audit

*Preserved research from an xhigh Luna read-only review on 2026-08-01. This is evidence and recommendation, not a decision record. The live plans and ADRs remain authoritative.*

## Executive conclusion

The divergence is mostly a deliberate product/API projection, not accidental duplication. MiniLcm exposes a smaller, portable semantic model; LcmCrdt adds CRDT identity, ordering, persistence, and intent/history; LibLCM remains the richer FieldWorks object model.

A broad breaking â€œv2â€ that renames MiniLcm/LcmCrdt to match LibLCM is not currently justified. It would reduce visible naming friction but would not eliminate the harder shape differences: `Entry` versus `LexEntry`, direct POS versus `MorphoSyntaxAnalysis`, flattened complex-form references, CRDT ordering, writing-system representation, and reduced mobile semantics.

Maintainers should be asked for a v2 *compatibility policy and canonical crosswalk*, but the recommended implementation is:

1. Keep existing public names and wire discriminators.
2. Make the MiniLcm â†” LibLCM name/shape map a versioned artifact.
3. Generate mechanical adapters and coverage reports from `MasterLCModel.xml` plus that map.
4. Add source aliases or deprecated wrappers only where semantics are genuinely equivalent.
5. Preserve old JSON/CRDT change names through deserialization aliases.
6. Reserve a breaking v2 for a demonstrated need from clients or a future LibLCM model-generation boundary.

This conclusion is consistent with Motifâ€™s explicit requirement for a hand-maintained name map because the names â€œdo not match,â€ and with ADR 0014â€™s decision to generate a LibLCM-shaped CRDT layer rather than make MiniLcm itself identical to LibLCM ([CONTEXT.md:92](C:/Users/johnm/Documents/repos/motif/CONTEXT.md:92), [README.md:51](C:/Users/johnm/Documents/repos/motif/README.md:51), [ADR 0014:68](C:/Users/johnm/Documents/repos/motif/docs/adr/0014-generate-the-crdt-layer-from-masterlcmodel.md:68)).

## Architecture boundary

LibLCM is the FieldWorks linguistic data model ([official repository](https://github.com/sillsdev/liblcm)). LexBoxâ€™s FieldWorks Lite backend separately contains MiniLcm, LcmCrdt, and the FwData bridge ([official FwLite tree](https://github.com/sillsdev/languageforge-lexbox/tree/develop/backend/FwLite)).

The effective boundary is:

`LibLCM / .fwdata` â†” `FwDataMiniLcmBridge` â†” `IMiniLcmApi` â†” `MiniLcm or LcmCrdt` â†” `Harmony sync / mobile / web`

Harmony changes represent user intent and are persistent synchronization history, rather than LibLCM property mutations ([Harmony README](https://github.com/sillsdev/harmony)). FieldWorks Lite deliberately supports a reduced editing surface across Windows, Android, and Linux, with some list-management operations remaining FieldWorks-only ([FieldWorks Lite documentation](https://software.sil.org/fieldworks/download/fieldworks-lite/)).

## Classification summary

- **Deliberate simplification or product/API abstraction:** most lexical, sense, rich-text, ordering, identity, view, comments, and CRDT-operation differences.
- **Historical/product naming:** `Entry`/`LexEntry`, `Sense`/`LexSense`, `ComplexFormType`/`LexEntryType`, and `MorphType`/`MoMorphType`. The repository proves the names differ and requires a map, but does not document why each name was chosen.
- **Uncertain:** `Publication`, `WritingSystem`, and morph-type creation. The code proves capability or representation mismatches, but not whether they are intentional product boundaries, transitional implementation, or backlog items.
- **Accidental:** I found no positive evidence that the main divergences are accidental. One unresolved repository-drift item is that Motif guidance names `SIL.LCModel 11.0.0-beta0150`, while LexBoxâ€™s package props use `11.0.0-beta0165` ([Directory.Packages.props:116](C:/Users/johnm/Documents/repos/languageforge-lexbox/backend/Directory.Packages.props:116)). This should be confirmed rather than presumed to be a bug.

## Effects by consumer

- **LexBox:** The bridge and `IMiniLcmApi` are the compatibility seam. Renames affect `FwDataMiniLcmBridge`, LcmCrdt registrations, sync helpers, EF configuration, and tests.
- **FieldWorks Lite:** Android, iOS, Mac Catalyst, and Windows share MiniLcm/LcmCrdt; the fwdata bridge is conditionally enabled for Windows ([FwLiteMaui.csproj:5](C:/Users/johnm/Documents/repos/languageforge-lexbox/backend/FwLite/FwLiteMaui/FwLiteMaui.csproj:5), [FwLiteMaui.csproj:26](C:/Users/johnm/Documents/repos/languageforge-lexbox/backend/FwLite/FwLiteMaui/FwLiteMaui.csproj:26), [FwLiteMaui.csproj:93](C:/Users/johnm/Documents/repos/languageforge-lexbox/backend/FwLite/FwLiteMaui/FwLiteMaui.csproj:93)). A full LibLCM type adoption would increase mobile coupling and would not provide the current portability boundary.
- **Web and TypeScript clients:** Reinforced.Typings exports MiniLcm/LcmCrdt model types and APIs. ## Recommended alternatives

1. **Versioned mapping metadata â€” recommended.** Include LibLCM class/field, Mini type/field, cardinality, normalization, identity, lossiness, read/write support, JSON name, and migration status.
2. **Generated mechanical adapters.** Generate straightforward field and relationship mappings from `MasterLCModel.xml` plus the map; keep semantic cases such as POS, complex forms, writing systems, publication types, and morph-type policy hand-written.
3. **Compatibility aliases.** Add deprecated C# names only for genuinely equivalent concepts. Do not alias `ComplexFormType` to `LexEntryType` or `Sense.PartOfSpeech` to `MorphoSyntaxAnalysis`.
4. **Wire aliases.** Preserve existing JSON and CRDT discriminators; allow new names as read aliases, while continuing to write the established canonical names during a migration window.
5. **Separate LibLCM-shaped namespaces.** Use generated LibLCM-shaped CRDT entities for Motif generation while retaining MiniLcmâ€™s product-facing API. This is already the direction of ADR 0014.
6. **Full v2 only if needed.** If maintainers choose a breaking rename, it should use a new package/assembly or explicit schema version, migration tooling, mixed-version sync tests, generated TypeScript aliases, and a published deprecation timeline.
