**contract**, in **upstream** (LibLCM / FieldWorks / PanGloss), and in our own **tooling**. Upstream
hazards are recorded because we must defend against them, not because we can fix them.

## A. Defects in shipped Motif code

| # | Issue | Status |
| --- | --- | --- |
| A1 | **Store cannot express amend.** `objects/<changeSetId>.json` is keyed by the frozen id, so amending would mutate a supposedly immutable object. Fix is the git model: object keyed by `intentDigest` (write-once), manifest keyed by `changeSetId` holding a movable pointer. | fixed |
| A2 | **`apply` is unbound.** `ChangeSetApplier.Apply` takes no Assessment, so [ADR 0004](adr/0004-prerequisite-graph-stable-ids-bound-apply.md) §3's "a bare apply is a hard error" is unenforced and the assess→apply TOCTOU window is open. | fixed |
| A3 | **`RollbackCacheInvalidator` could commit a mutation.** It called `ILexEntryRepository.ResetHomographs` → `LexDb.ResetHomographNumbers`, which wraps a project-wide `HomographNumber` reassignment in `DoUsingNewOrCurrentUOW`. **Correction to my original framing:** at the *existing* call site (inside the applier's catch block) the outer unit of work is still open, so `CurrentDepth > 0` and it would have *joined* that bundle rather than committing separately — the defect was **latent, not actively firing**. The real hazard is any future call site invoking rollback-cleanup after the unit of work has closed (`CurrentDepth == 0`), which is the documented usage and takes the `else` branch that opens a new task and commits. Fixed unconditionally rather than relying on that call-site nuance: it no longer calls `ResetHomographs` at all, and instead marks the cache non-reusable — the only correct response given C15. **Superseded 2026-08-06:** the type is deleted. A failed apply's catch block now does nothing at all, so there is no cleanup call site left to get wrong, at any `CurrentDepth` (ADR 0016 as amended). | fixed (code deleted) |
| A4 | **Assess can poison derived caches.** Assess mutates then rolls back on every call, and `UndoStack.Rollback` (unlike `Undo`) skips the forward-only-hook cache invalidation, leaving headword / homograph / monomorphemic caches stale. Dormant today only because `setGloss` touches none of them; **fires the moment a lexeme-form or citation-form operation exists**, which is the next operation we add. A second assess on the same cache could then return a different effect digest for identical state — breaking the determinism clause and "re-run and confirm no change." **Resolved differently 2026-08-06, and better:** the guard is gone because the cause is gone. A Dry Run mutates a single-use file copy and discards it — it never rolls back, so it never poisons anything, and no field needs classifying. ADR 0016 as amended; the `AssessPoisonsCache` column, `DerivedCachePoisoningOperationKinds` and `CacheReusability` are all deleted. This answers `C10a`. | fixed (cause removed) |
| A5 | **CLI draft file contradicts the in-memory-draft decision.** `drafts/<name>.json` exists because each CLI verb is a separate OS process, but S3 says drafts never touch disk. Documented as a deliberate session shim; a library or daemon consumer must keep drafts in memory. | fixed (documented) |
| A6 | **Baseline retention could never delete a published Baseline.** `BaselineRetentionCleaner.Clean` called `File.Delete` on `PublishedBaseline.Path`, but publication produces a **directory** — `BaselineBundleReceiver` moves the extracted bundle to a digest-named directory holding the `.fwdata`, `WritingSystemStore/` and `SharedSettings/`. `File.Delete` against a directory throws, the surrounding catch recorded a cleanup failure, and every later pass failed identically, so superseded Baselines would have accumulated without bound. `DeleteDirectory` existed on the file-system seam and was never called from `Clean`. Invisible because every test built the Baseline as a plain file with `File.WriteAllText` — a shape publication never produces. **This is the same fixture-shape blindness as the `SharedSettings` mutation:** the assertion was fine, the fixture was the wrong shape. Fixed by walking the tree bottom-up and re-checking ownership and reparse points at every level, matching `WorkspaceCleaner.DeleteTree` and `ProjectWorkspaceEvictor.DeleteTree`; the tests now build the production shape, and one asserts the directory is genuinely gone. Latent when found — the cleaner had no production call site, and would have armed with the first retention wiring. Rule adopted: **when a test builds a fixture by hand, check that its shape is one production actually produces.** | fixed |
| A7 | **A crash between publishing a Baseline and recording it orphans the directory.** `BaselinePublishCommandHandler` moves the verified bundle into place before writing the durable row — the right order, artifact before the row that claims it — and an in-process failure is compensated by `DeletePublicationIfOwned`. But if the process dies in that window no compensation runs, and nothing afterwards reconciles: `ReclaimIncomingDirectories` sweeps only `.incoming-*` staging names, never a fully-moved digest directory, and no query can see a directory that has no row. That directory is then unreachable by retention forever, unless the identical content is republished under the same digest. The consequence is a disk leak, not corruption or a misleading status — nothing reports the orphan as current. Not fixed by choice: the repair is a startup reconciliation sweep over digest directories with no `Baselines` row, which belongs with the retention/archive work that is not yet built, and whose own plan defers exactly these queries to an archive-integration checkpoint. | open |
| A8 | **`HeadlessLcmUi.ConflictingSave` silently discards a conflicted save while reporting success.** It returns `true`, and `true` means revert: `UnitOfWorkService.GetUserInputOnConflictingSave` calls `m_ui.ConflictingSave()` and on `true` runs `RevertToSavedState()`, then `SaveInternal` returns normally with no exception and no signal to the caller. The class doc claims the opposite intent — "destructive/ambiguous decisions fail loudly (`NotImplementedException`) rather than silently guessing" — and every other ambiguous callback in the type does exactly that. **Latent, and only by luck of the backend:** the path is reachable only when a foreign peer commits between this process's read and its save, which the exclusive `{project}.fwdata.lock` taken by `XMLBackendProvider` makes impossible today. It would arm immediately if Motif ever opened a project as a `kSharedXML` peer. [ADR 0040](adr/0040-one-api-the-cli.md) decision 6 rules that out on exactly this ground, so the defect is contained by architecture rather than by code. Fixed: it now throws `NotSupportedException` like every other ambiguous callback in the type, naming what happened rather than reporting the call unimplemented. Containment is now belt-and-braces — architecture keeps the path unreachable, and the code fails where a caller can see it if that ever changes. Note the second answer is no safer than the first: `false` keeps changes LibLCM has already judged unreconcilable, which is why refusing is the only correct response for a process with no person to ask. | fixed |

Fix by bounding every wait in the test (`WaitAsync(TimeSpan…)`) so it fails fast instead of hanging, rather than by relying on suite ordering. Related to D10 in kind: a test whose premise depends on winning a race the suite does not guarantee. | open |
| D12 | **`MismatchedResponseIdRejectsPendingRequest` asserted an exception that races its own teardown.** The test drove a fake worker into answering with a request id nobody was waiting for, then asserted `SendAsync` threw `InvalidOperationException`. Two things happen concurrently after that frame arrives: the read loop faults with "the worker response identifier is not outstanding" and calls `Close`, which disposes the stream; and the same connection's `SendAsync` may still be inside `FlushAsync` on that stream. When the disposal wins, `SendAsync` surfaces `ObjectDisposedException` ("Cannot access a closed pipe") instead, and the exact-type assertion fails. Seen once in a full-suite run and green both in isolation and on re-run, so it was load-dependent rather than a regression -- the third racy-test finding of this kind, after D10 and D11. **Fixed rather than recorded and left:** the connection's terminal reason does not race, so the test now asserts the send failed and separately that `Completion` faulted with the `InvalidOperationException` naming the unmatched id. That is strictly stronger than what it asserted before, because it pins *why* the connection died rather than inferring it from whichever exception the racing send happened to surface. | fixed |
| D13 | **`PublishVerifiedAsync_ValidatesAnEmptySharedSettingsInAnExistingPublication` failed once under a full gate and cannot be reproduced.** Observed on one `./test.ps1` run whose only working-tree change was two added assertions in an unrelated test file. It then passed 1/1 under a targeted filter and green on an immediate clean full run, so it is load-dependent rather than a regression — the fourth of this kind after D10, D11 and D12, and like D10 it is in a test that manipulates a real publication directory. **Not diagnosed, and worse, not diagnosable from what was kept:** the failure message was lost because the gate's output was filtered to the summary lines before it was read. The mechanism is therefore a guess, and is recorded as one. Next full-gate failure in this area must capture the whole output before anything else. | open |
| D14 | **A leftover `testhost` makes the gate look like a hang, and D11 predicted it.** After a subagent's own test run, `./test.ps1` was killed at 600 seconds having produced no output, on a suite that had been finishing in 40. It was not a hang in the code: with every stray `dotnet`/`testhost` process killed, the same tree ran green in 84 seconds, and `dotnet test --blame-hang --blame-hang-timeout 90s` named no test at all. The blocked step was the *build* — D11 already records that a hung `testhost` keeps a lock on the build output and that the next build then fails or stalls. What is new is the shape of the symptom: a stalled build inside a wrapper script that pipes through `grep` shows nothing whatsoever, so it reads as an infinite test rather than a blocked compile. Cheap mitigation: `test.ps1` could refuse to start while a `testhost` from a previous run is alive, and say so. Until then, kill stray processes before concluding anything from a gate that produces no output. | **fixed** -- `test.ps1` now stops before the build when a `testhost` is already running, naming the PIDs and the command to clear them, with `-AllowRunningTestHosts` for a deliberate second run. The stall it prevents printed nothing at all, so the guard's whole value is that it turns silence into a sentence. **One interaction to know about:** the refusal names no test result, so a caller waiting on `Tests OK` or `Tests failed.` matches neither and waits forever — an agent lost an hour to exactly that, polling a file the refused gate never wrote to. The guard is not the fault there; waiting on a gate instead of running it in the foreground is, and the refusal simply gives that habit a new way to hang. **The opposite mistake is just as easy and was made three times:** killing `testhost` and starting a gate immediately leaves the build output half-written, and the incremental build that follows does not recover — producing a run that reports *fewer tests than exist* with zero failures, which reads like a pass. One such run reported 1186 of 1302 passing and printed no `Tests OK` line. Kill stray processes, then let the build settle, and treat a total that dropped as a build artefact rather than a result. |
